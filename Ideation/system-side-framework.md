## What is known

The author has a **separate, complete framework for the system-side component**,
developed independently of ideas 1–5. It will be introduced in a later session.

Nothing about its content is known here. This file exists so that:

- the five captured ideas are read as **one half** of the picture, not the whole;
- no note in `Ideation/` is treated as settled on questions the system-side
  framework may already answer;
- the eventual introduction is a *merge*, not a retrofit.

## Why this matters for the existing notes

Several open questions in ideas 1–5 are plausibly system-side, and may already
be answered:

- **Where treatment attaches**, and the intra-processing sub-method — see
  [`scope.md`](scope.md).
- **The computable threshold** — "conclusive" in idea 2, the licensing bar in
  idea 4. A runtime threshold is a system-side quantity.
- **The update channel and its persistence** — idea 4's core experiment is a
  system behaviour before it is a conceptual claim.
- **The reference default** — idea 5's baseline is something an implementation
  must actually hold.

Treat all of these as **provisionally open**, not as gaps in the conceptual
work. Do not build elaborate answers to them in these notes before the
system-side framework arrives; the effort would likely be discarded, and worse,
it could bias the merge toward answers reached without it.

## On introduction

When it arrives, the merge should establish:

1. Which open questions above it closes outright.
2. Where the two frameworks **disagree** — the most informative outcome, and the
   one most easily lost if the newer material is simply appended.
3. Whether the diagnosis/treatment split survives contact with it, or whether
   the system-side structure suggests a different division.
